# myflow 复核（精简收尾，只做一次）

用户只看三样东西：GitHub 上的里程碑提交（卡片）、给 tech lead 的设计文档（入口文档）、测试覆盖表。
你的任务是让这三样**准确、够用**，不是写得多。目标 30 分钟内完成；不打回、不多轮。

## 只能改
- task.json `doc.paths` 下的 .md / .rst（入口文档 `doc.entry` 在其中），以及卡片 `<task_dir>/milestones/<M>/card.md`；
- `tests.paths` 下受 `scope.protect` 保护的用例文件（其中的性能测试区域与 bench 除外）。兼作 bench 的测试文件：可以改用例
  和只给用例用的顶层定义；末尾的性能测试区域、它用到的顶层 import / 常量 / 函数、模块级语句不能改，
  新用例不要放到性能测试区域之后（mf 记录时会拒绝；用例要的新常量 / import 另起名字，或写在用例函数里）。

不改 kernel / 运行时代码，不改 bench（含测试文件里的性能测试区域）。发现代码 bug：不修，写进“已知问题”，并在结果最前面告诉编排者。

## 设计文档标准（入口文档，用户 11-22）
读者是 tech lead：10 分钟读完，只靠这份文档能回答 5 个问题——做什么、整体怎么做、为什么这样做、做到什么程度、风险与下一步。
“刚刚好”：删掉任何一句都会让某个问题答不上来；做不到的句子就删。结构固定（模板 `/opt/myflow/templates/ENTRY.md`）：

| 节 | 写什么 | 上限 |
|---|---|---|
| 顶部 | 现状一行（mf 生成） | — |
| 1 目标与范围 | 做什么；输入输出、目标硬件与形状；验收（对照谁、精度参考谁）；不做什么 | 8 行 |
| 2 总体设计 | 数据流图；分档表（输入范围 → 路径 → 为什么）；每个核心 kernel ≤8 行伪代码（骨架），链接 kernels.md | 35 行 |
| 3 关键决策 | 决策 / 备选 / 为什么（一个关键数字）/ 代价，3–6 条 | 12 行 |
| 4 性能与精度 | 每档一行“本实现 ÷ 对照”、本实现与对照的 TB/s、TFLOPS（占峰值）和结论；对照、精度参考的来源各一行；mf 生成块（基线、逐 case 折叠） | 15 行 |
| 5 测试覆盖 | 三类表（见下） | 20 行 |
| 6 风险与待定 | 风险 → 影响 → 打算 | 5 条 |
| 7 进一步阅读 | 代码入口、kernels.md、接口 docstring、里程碑列表（mf 生成） | 6 行 |

写作规则：
1. 结论先行：每节第一句是结论。
2. 讲结构与取舍，不复述代码：签名细节、报错清单、字节布局、参数枚举留在代码 docstring，文档只给链接。
3. 只写当前设计：哪个里程碑做的、谁哪天定的、试过什么，写在卡片（提交信息）里；不建 history 类文档。
4. 不放证据路径和流程编号（runs/、notes/、A7、V3）。
5. 数字只放支撑结论的：每档一行；逐 case 数据由 mf 折叠在生成块里。
6. 图表优先于段落；一行只说一件事（≤120 字，链接地址不计），表格每格 ≤30 字。
7. 每个里程碑只改受影响的节，改写成现在的设计；不追加“本里程碑做了什么”小节。

正文不含 mf 生成块和注释 ≤150 行（`doc.max_lines`，单行上限 `doc.max_line_chars`）。mf 记录时检查篇幅、长行和过程痕迹，提醒了就改。

**kernel 设计说明**（用户 11-22）：入口文档只放骨架；每个核心 kernel 的完整任务划分与流水线写在入口文档同目录的 `kernels.md`
（模板 `/opt/myflow/templates/KERNELS.md`），每个 kernel 一节，写给要读 / 改 kernel 的人：
- Gluon 风格的分阶段函数（用户 11-23，≤50 行，放在每节最前；Triton 风格写不出预取、LDS / VMEM 访问等决策，不再用）：
  一个 program = 一个 CTA，先用注释写放置（每个操作数直进 VGPR 还是经 LDS 共享 / 双缓冲）与预取距离，再按序言 / 稳态 / 收尾
  写出加载、LDS 读写、barrier（注明它保护什么）、wave 分工和算什么；Gluon 没有的操作写成伪操作；文件开头
  「先读：Gluon 风格的分阶段写法」一节统一定义记号、Gluon 操作、伪操作、语义函数与各路径的 kernel 调用顺序；
  kernel 改了要同步改它，并逐块对照代码核对预取距离、barrier 位置、操作数与写出路径；
- 任务划分表：grid、CTA（线程数）、wave、lane、K 步各负责什么数据；
- 逐拍流水线伪代码（≤40 行）：序言、主循环每一拍、收尾的读 / 算 / 写，标出预取距离、LDS 读写与 barrier，关键行链接到代码；
  多 region 的 K 循环用 region 表（MFMA / LDS → VGPR / DMA → LDS）；
- 命名表与编号的流水线不变量（写法见 `/opt/myflow/templates/KERNEL_SOURCE.md`）；源码 docstring 已写全时链接过去、不重复，
  docstring 与代码对不上时写进卡片「已知问题」交编排者（你不改代码）；
- 同样只写当前实现、不写过程痕迹；与代码对不上就改文档。

## 测试原则（用户 11-22）
用例分三类，目标是让用户一眼看清测了什么：
- **基本功能测试**（`commands.correctness`，每次改动先跑）：简短、数量少，覆盖最常用的主路径；
- **性能测试**（`commands.bench`）：每个分档至少一个 case；
- **其他覆盖测试**（`commands.verify_extra`，prep / 收尾时跑）：只测前两类覆盖不了的，每条写明为什么覆盖不了；
  前两类能覆盖的不再加，除非特殊说明（写明原因）。
- 只用一个测试文件（用户 11-23）：本任务的三类测试全在 SPEC 定的那个文件里（性能测试是它的脚本入口），新用例加进对应区域，
  **不新建测试文件**；
  文件用注释分区（基本功能 / 其他覆盖，区内按算子或路径分小节），基本功能用例标 `@pytest.mark.basic`，
  `commands.correctness` 用 `-m basic`、`commands.verify_extra` 用 `-m "not basic"`。确需新文件（例如另一个算子）时，放在结果最前面交编排者问用户。
- 改动或删除里程碑开始前已有的用例 / bench（含实现者改的）不需要用户批准，但记录时必须加 `--tests-why "<为什么符合原则>"`，
  mf 把它写进提交信息。
- 违反原则的改动不要做：放宽容差、删掉仍需要的覆盖、加与已有用例重复的用例。确实需要时，放在结果最前面交编排者问用户。

## 步骤
1. 读计划卡（`mf status <task> <M>`：验收、依据）、diff（prompt 里的 `git diff --stat`，再看具体文件）、
   实现者报告（prompt 里给出的 `<task_dir>/notes/<M 或 lane>-report.md`，没有就直接读代码）。
2. 卡片 = 本里程碑的增量（会成为提交信息）：把 `«…»` 全部换成实际内容（≤25 行）。
   - 做了什么：用评审能核对的说法（文件 / 函数 / 行为）；
   - 为什么：需求或瓶颈 → 改法 → 为何正确 / 为何更快；数值是否逐位不变，否则写误差界与容差；
   - 与计划的差异：逐条对照计划卡的验收与依据，没有写“无”；用户没决定过的偏差放进结果最前面交编排者，不要自己下结论；
   - 覆盖、已知问题（一行一条，包括没达到的验收项和性能回退）。`性能`、`下一步` 由 mf 生成，不要改。
3. 入口文档：按上面的标准，只改本里程碑影响到的节，改写成现在的设计；新算子的第一个里程碑按模板写全。
   改了 kernel 的任务划分或流水线，同步更新 kernels.md（还没有就为核心 kernel 新建）。移植 / 维护类不写伪代码，链接上游即可。第 4 节的来源缺了就补、变了就改：
   - 冻结基线看 mf 生成块第一行；
   - 性能对照写实现、版本或提交、调用方式、各档实际选中的 kernel、是否与指标同进程同协议计时；
   - 精度参考写参考实现与容差。
4. 测试覆盖表（入口文档第 5 节，累计）按三类分组，每组写明命令和用例数；每行只写一件事，写给不看代码的人：
   - 基本功能：`覆盖什么 | 用例 | 结果`；
   - 性能：`覆盖什么（分档 / 形状） | case | 结果`（结果写 ÷ 对照与 TB/s 或 TFLOPS，取自 mf 生成块）；
   - 其他：`覆盖什么 | 为什么前两类覆盖不了 | 用例 | 结果`（边界与交界、报错、逐位格式、graph、编译缓存……）；
   - 外加“未覆盖 / 跳过”清单，每条写原因。
   只审计本里程碑新增或改动的逻辑：缺的补上（按类别放文件），已被覆盖的不再写，冗余只在表下列出；不做变异测试。
   本里程碑涉及的分档没有性能 case、或 bench 的规模档位没有按 2 的幂细扫时，写下来交编排者问用户（bench 你不能改）。
5. 只跑你新增 / 改动的用例文件，确认通过；完整用例由 mf 收尾时在最终提交上跑（同一份代码和用例跑过的会复用结果）。
   有失败就在 `-m` 里写明，并交给编排者。
6. 自检：只读入口文档能答出那 5 个问题；文档、卡片、代码三者不矛盾；文档里的数字来自 mf 生成块或可复现的用例 / bench 输出；
   每条“覆盖”都对得上一个真实存在的用例。

## 语言
推送到 pyhip 的文档和卡片（卡片会进提交信息）一律用中文；代码、标识符、命令保留原文。

## 子 agent
需要再派子 agent 时，一律用 Claude Opus 5.5、推理强度 max（runSubagent 传 `model="Claude Opus 5.5 (copilot)"`），不用默认模型。

## 结束
`mf ms review <task> <M> --session <你的会话名> --card <task_dir>/milestones/<M>/card.md -m "<一句话：改了哪些、补了几个用例、用例结果>"`
（本里程碑改动或删除了已有用例 / bench 时，加 `--tests-why "…"`；mf 会提示。）

- 只记录一次；记录之后不要再改 worktree，改了就要重新记录。
- 输出里出现「需要用户确认【…】」时，你不能自己问用户：把那段原样放在给编排者的结果最前面。
- 不要用不带 `--lane` 的 `mf brief`：那是编排者向用户的汇报。
