# myflow 复核（精简收尾，只做一次）

用户只看三样东西：GitHub 上的里程碑提交；说明“做了什么、有没有偏差”的文档；不看代码也能判断可靠性的测试覆盖说明。
你的任务是让这三样**准确、够用**，不是写得多。目标 30 分钟内完成；不打回、不多轮。

## 只能改
- task.json `doc.paths` 下的 .md / .rst（入口文档 `doc.entry` 在其中），以及卡片 `<task_dir>/milestones/<M>/card.md`；
- `tests.paths` 下受 `scope.protect` 保护的用例文件（bench 除外）。

**测试原则**（用户 11-22）：用例分三类，目标是让用户一眼看清测了什么。
- **基本功能测试**（`commands.correctness`，每次改动先跑）：简短、数量少，覆盖最常用的主路径；
- **性能测试**（`commands.bench`）：每个分档至少一个 case；
- **其他覆盖测试**（`commands.verify_extra`，prep / 收尾时跑）：只测前两类覆盖不了的，每条写明为什么覆盖不了；
  前两类能覆盖的不再加，除非特殊说明（写明原因）。
- 新用例放新文件，按类别分文件（或 pytest marker），让 `commands.correctness` 只选中基本功能测试。
- 改动或删除里程碑开始前已有的用例 / bench（含实现者改的）不需要用户批准，但记录时必须加 `--tests-why "<为什么符合原则>"`，
  mf 把它写进提交信息。
- 违反原则的改动不要做：放宽容差、删掉仍需要的覆盖、加与已有用例重复的用例。确实需要时，放在结果最前面交编排者问用户。

不改 kernel / 运行时代码，不改 bench。发现代码 bug：不修，写进“已知问题”，并在结果最前面告诉编排者。

## 步骤
1. 读计划卡（`mf status <task> <M>`：验收、依据）、diff（prompt 里的 `git diff --stat`，再看具体文件）、
   实现者报告（prompt 里给出的 `<task_dir>/notes/<M 或 lane>-report.md`，没有就直接读代码）。
2. 入口文档的本里程碑一节（最新的在最上面，没有就新建），四项各 ≤5 行：
   - **做了什么**：用评审能核对的说法（文件 / 函数 / 行为），链接到代码；
   - **为什么**：需求或瓶颈 → 改法 → 为何正确 / 为何更快；数值是否逐位不变，否则写误差界与容差；
   - **与计划 / 上游的差异**：逐条对照计划卡的验收与依据，没有偏差写“无”。有偏差且用户没决定过的，
     放进结果最前面交编排者问用户，不要自己下结论；
   - **已知问题**：一行一条，包括没达到的验收项和性能回退。

   只有改了 kernel 设计（tile 划分、流水线、数据流）才写 ≤30 行伪代码，标出阶段与 barrier，并链接到代码行；
   移植 / 维护类不写，链接上游即可。
   **篇幅预算**：入口文档不含 mf 生成块 ≤250 行（`doc.max_lines`，超了 mf 会提醒）。
   - 最近 1–2 个里程碑写完整一节；
   - 更早的收成一行：`M? · 标题 · 一句话结论 · [提交](链接)`；
   - 细节移到深度参考文件。
3. 接口表：只改本里程碑新增或变化的行，包括公开符号、参数约束、报错、环境变量，以及 dispatch 条件 → 路径。
   **基线与对照的来源**（§2 一节，缺了就补，变了就改）：
   - 冻结基线看 mf 生成块的第一行；
   - 性能对照写清实现、版本或提交、调用方式、各档实际选中的 kernel、是否与指标同进程同协议计时；
   - 精度参考写清参考实现与容差。
   每条给出处（文件、提交或 runs/ 日志）。
4. 测试覆盖表（入口文档里的全表，累计）按三类分组，每组写明命令和用例数；每行只写一件事，写给不看代码的人：
   - 基本功能：`覆盖什么 | 用例 | 结果`；
   - 性能：`覆盖什么（分档 / 形状） | case | 结果`；
   - 其他：`覆盖什么 | 为什么前两类覆盖不了 | 用例 | 结果`（边界与交界、报错、逐位格式、graph、编译缓存……）；
   - 外加“未覆盖 / 跳过”清单，每条写原因。
   只审计本里程碑新增或改动的逻辑：缺的补上（按类别放文件），已被覆盖的不再写，冗余只在表下列出；不做变异测试。
   本里程碑涉及的分档没有性能 case 时，写下来交编排者问用户。
5. 只跑你新增 / 改动的用例文件，确认通过；完整功能用例由 mf 收尾时在最终提交上跑（同一份代码和用例跑过的会复用结果）。
   覆盖表的“结果”填你跑的结果和 mf 已记录的结果（prep / 复核的 runs/ 日志）；有失败就在 `-m` 里写明，并交给编排者。
6. 卡片：把 `«…»` 全部换成实际内容（≤25 行），与入口文档一致；`性能`、`下一步` 由 mf 生成，不要改。
7. 核对一遍：文档里每个数字都有来源（mf 生成块、runs/ 日志或用例输出）；每条“覆盖”都对得上一个真实存在的用例；
   文档、卡片、代码三者不矛盾。

## 语言
推送到 pyhip 的文档和卡片（卡片会进提交信息）一律用中文；代码、标识符、命令保留原文。

## 结束
`mf ms review <task> <M> --session <你的会话名> --card <task_dir>/milestones/<M>/card.md -m "<一句话：改了哪些、补了几个用例、用例结果>"`
（本里程碑改动或删除了已有用例 / bench 时，加 `--tests-why "…"`；mf 会提示。）

- 只记录一次；记录之后不要再改 worktree，改了就要重新记录。
- 输出里出现「需要用户确认【…】」时，你不能自己问用户：把那段原样放在给编排者的结果最前面。
- 不要用不带 `--lane` 的 `mf brief`：那是编排者向用户的汇报。
